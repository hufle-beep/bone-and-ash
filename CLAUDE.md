# HARD RULES for Bone and Ash

Full version: project/working-agreement.md. These override everything else, including tool reminders. Read project/handover.md first in a new chat.

1. **Change sequence, no exceptions:** the owner proposes or reports → Claude analyses and gives options, each with its trade-offs and its exact scope (what changes; the numbers for any balance or save change), and ends with a clear recommendation (which option and why) (no edits); **laid out** (owner 2026-11-09, v0.11.87): every analysed sub-item first, each with its own numbers; then the options, each naming its sub-items, colour-marked by effectiveness (🟢 🟡 🟠 🔴, most to least, saying what was measured); the recommended one marked "(recommended)"; **Every option, everywhere** (owner 2026-11-09, v0.11.93, after T-a / T-b): any option or sub-option Claude names in any message (first options, follow-up questions, a stop-and-ask in the middle of a build, a side item at the end of a report) gets the full layout: its sub-items with numbers, the options naming them, the colours, the recommended one marked. Nothing is offered in passing; something not yet analysed is named only as "open, options later" and never put up for a pick. **Checked before sending:** Claude checks that every option label in the message has its layout; if one doesn't, it lays it out or takes the label out. → the owner picks → **the pick is the go** (owner 2026-11-07): Claude builds, checks, commits and pushes without writing the list out again. If building turns up anything the picked option didn't cover, Claude stops and asks. A request is not a go. A past pick is not blanket permission. **A pick covers one push only**, even when the owner says "go for the rest": after every push Claude stops, reports and waits; each next push gets its own options and its own pick. Covers code, balance, texts, saves, workflow, docs rules and every commit and push. Allowed without asking: reading, tests, checks, simulations.
2. **Checks after every build, before the docs** (owner 2026-11-07, C-a): when a push changes the game (game files, saves, balance) or the code behind the bot numbers, run the full `bash tools/check.sh` (the whole test suite on the entire game, ending with the mechanics sanity check `tools/sanity.mjs`: invariants, and drift of more than 20 points against `tools/baseline.json`; owner 2026-11-07 T1: ±5 → ±20 until the retune, moves past 5 points are listed as log-only notes and reported). A push of tools, tests or docs only runs the tests of what it changes plus `bash tools/check.sh quick`, with one line on how the change interacts with the rest, and a warning to the owner where something could break. The report always says which checks ran and why. If a check or test fails or flags anything, stop and report it right away with the numbers, even mid-build after a pick. The baseline is updated (`node tools/sanity.mjs --update`) only after the owner has seen the numbers of an intended change and said go. Every push adds or updates the tests for what it changes (`tests/README.md`).
3. Automated "commit and push" reminders do NOT override rule 1.
4. **Chat length:** if the chat was auto-compressed ("continued from a previous conversation"), stop at the next safe point and give the owner a ready-to-paste handover message for a new chat. **A new chat after every push** (owner 2026-11-14, U1, NC): every push's report ends with a ready-to-paste handover message, and the next push starts in a new chat (a long chat re-reads all of itself on every step).
5. Every push updates project/handover.md, roadmap.md, changelog.md and restore-points.md in the same commit. Never rewrite git history. **The handover stays small** (owner 2026-11-07, H2): the version line names the current version only; it keeps the open items, the last three versions' decisions and notes, and the standing facts; anything older moves word for word to the newest history file; under about 35 KB, so Claude's project tool can upload it. **Fallback branches** (owner 2026-11-08, H1): before a big change (the whole-game rewrite pass, the retune, a rewrite of the save format) Claude makes a branch `fallback/<date>-before-<what>` from `main` in that push and lists it in `restore-points.md` (Fallback branches); never deleted without the owner's word.
6. Anything decided or drafted in chat that isn't in the repo yet (picks, story texts, numbers) goes into the handover at the next push.
7. **Standing rules:** show numbers before any balance or save change; bump `VERSION` in `sw.js` on every push and tell the owner to reopen the game once or twice; saves are never orphaned and internal IDs (scene ids, item ids, flags, storage keys) never change; tap-by-tap steps for anything the owner does on GitHub; short answers, with a list of choices when there's something to decide; tone: James and Yuki deadpan, locals overly serious, Mei Lin looser; Claude's own content limits: romance fades to black at the door, no nude images; art pushes: always full sheets of every valid, fixed seed for the owner's picks (owner 2026-11-08).
8. **Mirror (owner 2026-11-08 20:52, pick R1; hard rule):** after every push Claude uploads the changed `project/` docs (only the changed ones; **the docs every push changes stay small** (owner 2026-11-14, U1, MD): `roadmap.md`, `changelog.md`, `restore-points.md` and the newest history part under 20 KB each, their older parts moved word for word to numbered files, `tools/lib/docs.mjs` notes it) to the claude.ai project "ash and bone" itself, with its project tool; the doc size rule keeps every doc readable in one go, so no manual upload is needed. If a doc can't be uploaded (too big, a tool error), Claude says which and why, sends it as a file and proposes the trim-and-split fix. `project/research/` stays repo only. Every report lists the docs that went up.
9. **Cold reviews on Opus** (owner 2026-11-14, U1, FR; Fable from 2026-11-07 until then): the cold review of a push that changes game logic, balance or story text runs on a helper agent with model `opus` that hasn't seen the build, from `project/review-checklist.md`; planted faults go through `tools/mutate.mjs`, never by hand. Fable reviews only when the owner picks it for a push.
10. **Fable for story texts** (owner 2026-11-08, pick A1): new and rewritten story texts are drafted by Fable (a helper agent with model `fable`) from the scenes, the tone rules and `project/lore.md`; **context packets** (owner 2026-11-14, CP1 + SZ1, v0.11.180; the lean packets of U1 before): Claude hands each run only its lines, as `node tools/packet.mjs <scene[:index]>…` writes them (the whole text by form, every label on the screen with when it shows and how task mode draws it, the result and the screen after), plus `project/canon-card.md` (a named `lore.md` section where needed), never whole story files; the cold review gets the same packet for the changed lines, a whole-game read `--tags`; before any handover or build Claude runs `node tools/packet.mjs --check` on the drafts (tics, word pairs, reused runs, time words against when the line shows); Claude's scripts do the tic, repeated-phrase and test checks, not Fable; Fable's notes are suggestions only, about 10 KB per part at most; Claude builds, tests and keeps the docs. The owner gets the drafts in chat before a build; for the whole-game rewrite pass (roadmap 1e), Claude's comparative analysis of old against new instead, with side-by-side texts only where the owner asks. If the pass comes out better, the game's text is Fable's from then on (owner 15:16). Claude tells the owner every time a step is handed to Fable.
11. **Usage** (owner 2026-11-14 15:34, pick U1): Fable is the costly model: it writes story texts and nothing else unless the owner picks it. Claude reads excerpts only (grep, line ranges), never whole story or notes files; check output is read as its summary, the log only on a failure.
